# 1.4.7：文件打开即时唤醒与页签复用

> 需要手动 reload 或安装 1.4.7。优化的是本插件的导航等待；真实文件管理器首次冷启动、目录扫描和内容渲染仍由宿主负责，本次没有承诺或测量原生窗口零延迟。

## 改动

- 打开请求不再等待 `replyCards` 的约两秒刷新，也不排在慢 Git/历史任务后。
- 活跃会话保持一个最长 1.5 秒的有界等待；收到点击请求立即唤醒，1.5 秒不是点击后必须等待的时间。
- 成功/失败回执立即唤醒等待界面，去掉固定 300 ms 轮询间隔。
- `openFile` 的桥接准入独立于普通请求的响应等待；两类流量仍共享每秒最多六次的限流和负载/超时边界。
- 文件管理器页签复用原标识及既有状态，仅更新定位路径；当前页签已显示同一文件时不重复打开。
- 切会话和卸载取消旧监听；宿主模块异步加载后再次检查会话版本，阻止切走再切回时的迟到导航。
- 无新增权限，不修改宿主或文件管理器插件；文件名展开、复制、差异与本地 Git 功能保留。

## 证据 → 修复 → 代码

| 已定位原因 | 修复 | 路径 |
|---|---|---|
| 旧请求跟随历史刷新交付，还受串行后台任务影响 | 独立、即时唤醒的导航监听 | `src/core/file-open.ts`、`src/main.ts`、`src/renderer/file-open-channel.ts` |
| 桥接单一响应队列造成等待通知和普通动作互相阻塞 | 导航只串行准入，不串行等待响应，保留限流 | `src/view/transport.ts` |
| 重复打开同一目标仍更新页签 | 同一文件跳过重复动作，换文件复用页签 | `src/renderer/plugin-review-adapter.ts` |

## 性能测量

测量 10 次、每次间隔 600 ms，使用真实构建 main、真实文件路径检查、有界 transport、renderer 通道和页签适配器。历史刷新全程故意阻塞；宿主页签 store 是测试替身，未包含真实 Electron IPC 或原生内容渲染。

- 插件通道首开：**2.71 ms**。
- 后续切换中位数：**1.60 ms**；P95：**3.55 ms**（暖切换 9 次样本）。
- 全程保持一个文件管理器页签，路径正确，成功回执无固定等待。
- 原始数值及测量边界见 [性能记录](file-open-performance-1.4.7.json)。这些数字不是实际 PI-Desktop 窗口端到端耗时。

## 使用

保持本地 `plugin/` 安装路径后手动 reload，或安装 `plugin/dist/local.diff-view-1.4.7.piplug`。确保内置文件管理器和 renderer 扩展已启用。若更新后首次打开仍慢，需要区分宿主文件管理器冷启动与已打开页签内切换，不能用本次测试替身的数字代替原生耗时。
